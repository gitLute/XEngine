# XEngine: архитектура и правила разработки

Документ описывает, как должен быть устроен и как должен писаться движок XEngine.
Он же является техническим заданием на рефакторинг: текущее состояние кода перечислено
в разделе 3, целевое состояние — в разделах 4-18, порядок перехода — в разделе 17.

Документ написан под требования к проекту:

1. собственные интерфейсы и абстракции везде, где есть внешняя зависимость или платформенная часть;
2. рефакторинг ECS, при котором сущность не содержит компонентов, плюс полноценная интеграция Box2D;
3. полное портирование с OpenTK на Silk.NET;
4. рефакторинг подсистемы спрайтов;
5. проект остаётся игровым движком и не содержит игрового кода;
6. новая реализация сцен;
7. собственная математическая библиотека;
8. SOLID как основной принцип проектирования.

---

## 1. Краткое описание проекта

XEngine — 2D-игровой движок на C#/.NET с физикой Box2D v3, написанный поверх
OpenGL. Движок предоставляет:

- ECS (entity-component-system) с иерархией трансформаций;
- конвейер обновления на основе систем с приоритетами;
- сцены с переключением и выгрузкой ресурсов;
- рендеринг спрайтов, nine-slice спрайтов, линий и отладочной визуализации физики;
- ввод с привязкой действий и аналоговыми осями;
- 2D-физику на Box2D;
- управление ассетами и JSON-конфигурацию.

Слой игры (прототип GunFight, редактор и WinForms-оболочка) удалён из репозитория
коммитом `f6aa1d5`. Сейчас в репозитории лежит только библиотека ядра, хост-приложения
нет: окно, главный цикл и передача `dt` в движок должны появиться вместе с портом на Silk.NET.

## 3. Дефекты текущей реализации

Этот раздел нужен, чтобы этапы миграции можно было проверять: каждый пункт должен
перестать существовать после рефакторинга.

### 3.1. Структурные проблемы

Проверка замечаний по разбору кода с привязкой к строкам — в разделе 21.

| Проблема | Место | Следствие |
|---|---|---|
| Сущность хранит компоненты в своём словаре | `Base/Entity.cs` | нарушено требование «энтити не содержит компонентов»; владение данными размазано между сущностью и сценой |
| Тип компонента используется как ключ `Dictionary<Type, GameComponent>` | `Base/Entity.cs` | на каждый `Get<T>` — хеширование типа, аллокации на boxing при проверках, нет плотного хранения |
| `Entity.AddComponent<T>()` молча перезаписывает существующий компонент | `Base/Entity.cs` | потеря состояния без диагностики |
| `GTransform` создаётся в конструкторе `Entity` как побочный эффект | `Base/Entity.cs` | трансформация неотличима от обычного компонента, но участвует в иерархии отдельно от остальных данных |
| Каждая сущность имеет `GScene Scene` | `Base/Entity.cs` | каждая сущность удерживает ссылку на сцену; при выгрузке сцены удерживается весь граф объектов |
| Запросы — линейный перебор всех сущностей на каждый вызов | `GScene.Query<T1,T2,T3>` | O(n) на кадр на каждый запрос; при 10 запросах и 10 000 сущностях — 100 000 проверок словаря за кадр |
| Все шесть перегрузок `Query` возвращают `IEnumerable` через `yield return` | `GScene` строки 186-261 | компилятор генерирует класс-итератор: аллокация на каждый вызов, то есть на каждый кадр в каждой системе и в каждом рендер-модуле |
| Нет кеша запросов и учёта структурных изменений | `GScene` | нельзя перейти к плотным массивам без переработки API запросов |
| Камера создаётся как сущность и живёт в общем списке | `GScene` строки 36-38 | камера — сервис уровня сцены, а не элемент игрового мира; участвует в `Query` наравне с объектами и удаляется вместе со всеми |
| `SetDirty()` рекурсивно обходит всё поддерево | `GTransform.SetDirty` строки 94-105 | перемещение корня сцены даёт O(N) на каждое изменение позиции родителя |
| `ClearScene()` объявлен, но нигде не вызывается | `GScene.ClearScene` строка 67 | метод `protected` и мёртвый: очистка сцены от сущностей не выполняется ни при выгрузке, ни где-либо ещё |
| `GScene.IsDeleted` проверяется, но никогда не выставляется | `GScene` строки 21, 139 | ранний выход из `Update` недостижим; признак удаления сцены не работает |
| Порядок освобождения зависит от обхода словаря | `GScene.RemoveDeleted` | `SetParent(null)` выполняется до `Dispose`, и обе операции следуют в порядке обхода `Dictionary`, а не в заданном порядке |
| Идентификаторы сущностей монотонно растут и не переиспользуются | `GScene._id` | рост потребления памяти со временем; нет поколения, поэтому «протухший» id неотличим от живого |
| `Entity.Dispose` вызывает `Dispose` компонентов, сцена удаляет сущности в `RemoveDeleted` | `GScene` | порядок освобождения ресурсов (Box2D-тело, текстура) нигде не гарантирован |
| Нет слоёв, нет порядка сущностей, нет сортировки отрисовки | `GScene` | порядок отрисовки определяется порядком обхода словаря, то есть случаен |

### 3.2. Ошибки в математике

| Ошибка | Место | Описание |
|---|---|---|
| `Homogenize` возвращает `new Vector4(v.X, v.Y, v.X, 1)` | `Utils/MathUtils.cs` | в позицию `Z` копируется `X`; при наличии родителя мировая координата `Z` считается неверно, а слой (сортировка) «едет» по X |
| `Rotate` использует знак `-s` | `Utils/MathUtils.cs` | направление вращения противоположно `FromPolar`, который документирован как поворот против часовой стрелки; интерполяция трансформации и поворот спрайта считаются в разных системах знаков |
| Документация `SizingPolicy` перепутана | `Common/Sprite/SizingPolicy.cs` | у `Source` написан комментарий «масштабирует относительно текстуры», фактически масштабирует относительно мира; у `World` — наоборот |
| `GSprite.GetSize` для `Source` использует `TextureSize.Y * _size.X` | `Common/Sprite/GSprite.cs` | вместо `_size.Y` спрайт растягивается по горизонтали; при неквадратной текстуре — искажение пропорций |
| Скалярный и матричный пути позиции считают поворот в разные стороны | `GTransform.RelativePosition` и `GTransform.GetWorldMatrix` | логика думала `(10,4)`, спрайт рисовался `(10,6)`: первая ошибка — `Homogenize` кладёт `v.X` в `Z`, вторая — порядок умножения матриц в OpenTK обратный к привычному. Нужны две явные функции |
| Нет библиотеки математики, математика размазана | `MathUtils`, `Box2D`-конвертации, `GSprite`, `GTransform` | одни и те же операции (поворот, lerp, move toward, AABB) реализуются в разных местах по-разному |

### 3.3. Проблемы подсистемы Box2D

| Проблема | Место | Следствие |
|---|---|---|
| Физический мир — компонент сущности | `GBox2DWorld` | физика объявлена частью игрового объекта; сцена обязана знать про `GBox2DWorld`, рендер-модули тоже |
| Тело Box2D — компонент с `Dispose` | `GBox2DBody` | `b2DestroyBody` вызывается даже для тела, которое не было создано (значение `B2BodyId` по умолчанию) |
| В `UserData` хранится ссылка на компонент | `Box2DCompat/UserData.cs` | пользовательские данные Box2D живут дольше компонента при отложенном удалении; обращение к освобождённому объекту из нативного колбэка |
| Идентификаторы тел не имеют обратной карты в сущности | `Box2DCompat` | каждый контакт делает `b2Body_GetUserData` + `GetRef<UserData>`; нет способа быстро найти сущность по `B2BodyId` |
| `GScene.Query` перечисляется дважды в одном кадре | `Box2DTransformSync.Update` | два полных обхода словаря на шаг физики; между обходами набор сущностей может измениться |
| Пиксели на метр живут в компоненте мира, но используются рендером | `GBox2DWorld.PPMScale` | рендер зависит от физического компонента; невозможно сцену без физики |
| Синхронизация основана на флаге `IsSynced` вручную | `GTransform`, `Box2DTransformSync` | флаг не сбрасывается после синхронизации, состояние «синхронизировано» живёт вручную и легко ломается |
| `IsSynced` никогда не возвращается в `true` | `GTransform` строки 24, 41, 131, 155 | выставляется в `false` в трёх местах и нигде не сбрасывается: у любой сдвинутой сущности `b2Body_SetTransform` шлётся каждый кадр, а документация Box2D 3.1 прямо предупреждает не задавать трансформ тела после создания |
| Не выставляются `enableContactEvents` и `enableSensorEvents` | `GBox2DWorld.Init` | `b2Types.b2DefaultWorldDef()` меняет только `gravity`. По документации Box2D 3.1 фигура порождает события касания только при `b2ShapeDef.enableContactEvents = true`, сенсоры выключены по умолчанию. `Box2DContactSystem` опрашивает обе очереди и молча получает пустоту; флагов нет и в `GBox2DBodyBuilder` |
| Тело без фигур не имеет массы | `GBox2DBodyBuilder.Build`, `AttacShapes` | фигуры прикрепляются отдельным вызовом после `Build`, поэтому тело без фигур — штатная ситуация: масса равна нулю, импульс не даёт эффекта, и ошибки не возникает |
| Запрет на иерархию реализован исключением в `SetParent` | `GTransform.SetParent` | проверка зависит от наличия компонента Box2D у сущности — нарушение разделения ответственности |

### 3.4. Проблемы сцен

| Проблема | Место | Следствие |
|---|---|---|
| Сцена сама создаёт камеру и физический мир в конструкторе | `GScene` строки 30-42 | нельзя создать сцену без физики или с другой камерой; порядок создания сущностей фиксирован |

| Переход между сценами реализован очередью из двух действий | `SceneManager.SwitchTo` | если вызвать переход повторно, возможна выгрузка сцены, которая ещё не загрузилась; нет состояний и защиты от повторного входа |

| Системы сцены хранятся в списке, сортировка по числовому приоритету | `GScene.AddSystem` | магические числа приоритетов (см. ниже), при двух одинаковых приоритетах порядок не определён |
| Сцена владеет `Random`, `Input`, `Assets`, `Camera`, `World` напрямую | `GScene` | сцена — «бог-объект», подменить любую зависимость нельзя, передача зависимостей в системы только через саму сцену |
| Нет фиксированного шага, нет ограничения максимального `dt` | `GScene.Update` | физика получает кадровый `dt`, при просадке кадров физика «телепортирует» объекты |

### 3.5. Проблемы рендеринга и спрайтов

| Проблема | Место | Следствие |
|---|---|---|

| Отсутствующая текстура молча заменяется на шахматный шаблон | `AssetManager.LoadTexture` | ошибка ассета не видна, объект невидим |

| `IsActionActive` требует наличия ключа в текущем и предыдущем кадре | `InputManager.IsActionActive` | «зажато» срабатывает только со второго кадра; ось ввода запаздывает на кадр |
| Сброс предыдущего состояния происходит в конце `Update` | `InputManager.Update` | оси читают состояние до сброса; при изменении порядка вызовов поведение незаметно изменится |
| Нет состояний мыши, окон, фокуса, текста | `Input` | для 2D-игры неприемлемо: нет курсора в мире, нет кликов, нет перетаскивания |
| JSON-конвертеры названы по OpenTK | `Utils/JSONConverters/OTKVector2Converter` | после порта имена вводят в заблуждение |
| `config.json` отсутствует в `Assets` | каталог пуст | конфигурация по умолчанию используется всегда, проверить загрузку нельзя |

### 3.7. Прочие

- `GameEngine` — класс без интерфейса; подменить его в тестах нельзя, а без него нельзя написать тест на цикл кадра.
- `RenderModule`/`RenderPipeline` не имеют интерфейсов; добавление нового бэкенда (Vulkan, программный растеризатор) потребует правок всех модулей.
- В `GameEngine.Update` нет ограничения `dt`, нет порядка «сначала ввод, потом сцена» (сейчас сцена обновляется раньше ввода — ввод одного кадра отстаёт на кадр).
- Публичные изменяемые поля в компонентах: `GBox2DBody.Id`, `OnCollisionEnter`, `OnCollisionExit`, `GBox2DWorld.PixelPerMetre`, `GSprite.FlipX/FlipY`, `GTrace.Color/MaxLength/IsAggressive`, `Axis.Positive/Negative`. Присваивание в обход метода не помечает кеш грязным, а компоненты — классы, поэтому правило «состояние только через методы» ничем не enforced.
- Нет тестов, нет `*.sln`, нет `.editorconfig`, нет настроек анализаторов, нет CI.
- Комментарии и документация есть только у части классов; у интерфейсов ввода и конвертеров — нет.

### 3.8. Ловушки переноса на Silk.NET

Эти проблемы не проявляются на OpenTK, но сломают сборку или поведение при порте.
Подробная проверка — в разделе 21.8.

| Проблема | Место | Следствие |
|---|---|---|
| `VertexAttribPointer` вызывается с `int` в `stride` и `offset` | `UnitQuad.Init`, `LineBatcher.Init` | в Silk.NET сигнатура требует `uint` и `IntPtr`; при переносе вызов не совпадёт и потребует явного приведения, иначе выберется перегрузка с `GLEnum` |
| Имена перечислений уточнены в Silk.NET 3.x | `Shader`, `LineBatcher`, `RenderPipeline` | `ShaderParameter` становится `ShaderParameterName`, `GetProgramParameterName` — `ProgramPropertyName`; таблица соответствия в разделе 15 требует сверки по `PublicAPI.Shipped.txt` |
| Нативные библиотеки GLFW и GL-контекст нужны на машине | новая инфраструктура | на CI без дисплея тесты с окном не запустятся; тесты обязаны обходиться без окна |

## 4. Принципы проектирования

### 4.1. Общие правила

1. Один тип — один файл, имя файла совпадает с именем типа.
2. Одна причина для изменения: если класс меняется по двум несвязанным поводам, он делится.
3. Зависимости объявляются через конструктор и через интерфейсы; доступ через глобальные переменные и статические сервисы запрещён.
4. Внутренние детали не публикуются: поля — `private`, состояние наружу выдаётся через методы и структуры-значения.
5. Публичные API помечаются XML-документацией. Для публичного API допускается только то, что покрывается тестом.
6. Никаких «магических чисел» в коде: константы с именами или вынесенные в настройки.
7. Исключения — для программных ошибок (неверное состояние, нарушение инварианта), не для штатных игровых ситуаций (смерть объекта, отсутствие ассета — это `Debug`-сообщение и подстановка значения по умолчанию).

### 4.2. Трактовка SOLID под задачи движка

| Принцип | Как применяется в XEngine | Пример из текущего кода, который нарушает принцип |
|---|---|---|
| SRP | `Entity` — только идентичность; хранилище компонентов; иерархия трансформаций; жизненный цикл сцены; рендер — разные типы | `GScene` одновременно контейнер сущностей, фабрика сущностей, менеджер систем, менеджер таймеров, очередь отложенных действий, владелец физического мира и камеры |
| OCP | Добавление нового рендер-прохода, бэкенда физики, бэкенда ввода не требует правок существующего кода | `RenderModule` жёстко завязан на `GLProvider` и OpenTK; добавление Vulkan-бэкенда потребует изменений во всех модулях |
| LSP | Наследники подставляются вместо базовых типов без изменения поведения | нет базовых типов с контрактом; когда появятся, запрещено наследование от `sealed` и нарушение контракта в наследниках |
| ISP | Интерфейсы узкие; система получает ровно те зависимости, которые использует | `IInputConfig` смешивает чтение состояния, обновление и изменение привязок; рендер-пасс получает весь `GLProvider` |
| DIP | Зависимости направлены внутрь: прикладной код знает только свои интерфейсы; бэкенды (Silk.NET, Box2D) реализуют их | `GameEngine` напрямую создаёт `OpenTK`-зависимые объекты, а рендер напрямую вызывает `GL.*` |

### 4.3. Направление зависимостей

Правило: **`Core` не знает о Silk.NET, Box2D и OpenTK**. Зависимости идут от периферии к ядру.

```text
                    ┌───────────────────────────────┐
   Samples/Sandbox →│  XEngine (фасад + composition) │←── тесты
                    └───────────────┬───────────────┘
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        ↓                           ↓                           ↓
  XEngine.Windowing            XEngine.Input              XEngine.Physics
  (Silk.NET + GLFW)            (Silk.NET.Input)           (Box2D.NET)
        │                           │                           │
        └───────────────────────────┼───────────────────────────┘
                                    ↓
                          XEngine.Graphics
                       (абстракции + Silk.NET OpenGL)
                                    ↓
                              XEngine.Core
                        (ECS, сцены, время, ассеты)
                                    ↓
                             XEngine.Mathematics
                          (векторы, матрицы, углы)
```

Проверка правила: если в `XEngine.Core` или `XEngine.Mathematics` встретился `using Silk.NET` или `using Box2D.NET` — это ошибка, она ловится ревью и запретом в `.editorconfig` (см. раздел 16).

Движок не должен жёстко ссылаться на конкретную реализацию: `XEngine` собирает

```csharp
var builder = new GameHostBuilder()

using IGameHost host = builder.Build(options);
host.Run(new SandboxApplication());
```

Так тесты подставляют заглушки (`NullGraphicsBackend`, `FakeInputBackend`,
`DeterministicTimeSource`), не требуя окна и GPU.

- В `assets/` лежат шейдеры и конфигурация, которые переиспользуются несколькими

- Legacy-каталог `XEngine/` не пополняется и удаляется на этапе 10.

## 6. Математическая библиотека `XEngine.Mathematics`

### 6.1. Выбор основы

Основа — **`System.Numerics`** из BCL: `Vector2/3/4`, `Matrix3x2`, `Matrix4x4`,
`Quaternion`, `Plane`. Обоснование:

- ноль внешних зависимостей, `XEngine.Mathematics` ссылается только на `net10.0`;
- `System.Numerics` не привязан к платформе, поэтому ядро остаётся независимым
  и от Silk.NET, и от Box2D, и от бэкенда рендера;
- в BCL нет игровых примитивов (углы с нормализацией, прямоугольники, капсулы,
  интерполяция с независимостью от кадра, детерминированная случайность) —
  их и пишем сами.

Отклонённые варианты:

| Вариант | Почему не берём |
|---|---|
| `NumSharp` | порт NumPy для научных вычислений: API `NDArray`, срезы, n-мерные массивы. Нет типов для графики, всё оперирует `float[]` с аллокациями — непригоден для горячего пути кадра |
| `Silk.NET.Maths` | качественная библиотека, но связала бы `XEngine.Core` с Silk.NET и нарушила правило «ядро не знает о бэкенде» |
| `MathNet.Numerics` | строгая линейная алгебра для науки (`double`, плотные матрицы, аллокации). Для рендера неудобна, игровых типов нет |
| собственные `Vector2/Matrix4` с нуля | дублирование BCL вручную: лишний код, лишняя цена ошибок, нулевая выгода |

Преобразования в `Silk.NET.Maths` и `Box2D.NET` выполняются **в бэкендах**
(`XEngine.Graphics.OpenGL`, `XEngine.Physics.Box2D`), а не в математике.

### 6.2. Реализовано

### 6.3. Правила математики

1. Типов из BCL не дублируем: добавляем только то, чего в них нет.
2. Углы в публичном API — тип `Angle`, а не «число в радианах».
3. Порядок обхода и знаки фиксированы: угол против часовой стрелки, ось Y вверх.
4. Сглаживание только через `Interpolation.Damp`, а не `Lerp(value, target, dt * k)`:
   только `Damp` не зависит от частоты кадров.
5. Каждая операция имеет один контракт и покрыта тестом.

### 6.4. Что исправлено по сравнению с текущим кодом

| Было | Стало | Где |

| `GTransform.Approach` = `Lerp(pos, target, strength)` | `Interpolation.Damp` с независимостью от кадра | `Interpolation.cs` |

## 7. ECS

### 7.1. Ключевое требование

**Сущность не содержит компонентов.** Сущность — это идентичность и ничего больше.
Все данные живут в хранилищах, принадлежащих миру (или сцене).

```csharp
/// <summary>Идентификатор сущности: индекс в плотном массиве плюс поколение.</summary>
public readonly struct Entity : IEquatable<Entity>
{
    public readonly int Index;
    public readonly uint Generation;
    public static readonly Entity Invalid = default;
    public bool IsValid => Generation != 0;
    public static implicit operator uint(Entity e) => ...;  // ключ словарей
}
```

Поколение в идентификаторе решает проблему «протухших» ссылок: после удаления сущности
её старый `Entity` сравнивается с текущей сущностью на том же индексе как неравные,
и обращение к удалённой сущности даёт `false` у `Has<T>`, а не чужую сущность.

### 7.2. Мир

```text
World (или SceneRoot)
├── EntityRegistry        слоты, поколения, свободный список, отметки удаления
├── ComponentStorage      набор ComponentStore<T> по типам компонентов
├── TransformGraph        иерархия: родитель, дети, локальные и мировые матрицы
├── SystemGroups          конвейер обновления (см. раздел 8)
├── TimeContext           dt, elapsed, номер кадра, масштаб времени
├── CommandBuffer         отложенные структурные изменения и события
└── Services              доступ к сервисам (лог, ассеты, физика, ввод, случайность)
```

`World` — единственный владелец всех данных сцены. Сцена — это конфигурация мира
(какие системы добавлены, какой рендер-пасс, какой бэкенд физики), а не владелец данных.

### 7.3. Компоненты

Два вида компонентов — разделение по требованию к памяти и по способу доступа:

| Вид | Интерфейс-маркер | Хранение | Для чего |
|---|---|---|---|
| Структурный | `struct T : IComponent` | плотный массив, без ссылок, возможен SoA | трансформ-данные, спрайты, физические тела, урон |
| Ссылочный | `class T : IComponent` | плотный массив ссылок | поведение, скрипты, ссылки на ресурсы |

Компонент не знает про сцену и не делает `Owner.Scene.X`. Вместо этого:

- доступ к контексту передаётся в методы систем;
- компоненты, которым нужна «пожилая» логика (регенерация здоровья, мигание, время жизни),
  получают тик от своей системы, а не от самих себя через `Scene.RegisterTimer`;
- компонент, которому нужна отложенная операция, получает `ref CommandBuffer`.

Компоненты, которые хранят ресурсы (дескрипторы GPU, тела Box2D), реализуют
`IDisposable` — вызывается централизованно при удалении сущности, в правильном порядке
(сначала события, потом ресурсы, потом слот освобождается).

### 7.4. Хранилища и запросы

```csharp
public interface IComponentStore
{
    Type ComponentType { get; }
    int DenseCount { get; }
    void EnsureCapacity(int capacity);
    bool Has(Entity e);
    void Remove(Entity e);
    void Clear();
}
```

- Плотный массив компонентов + разреженная карта `Entity.Index -> dense slot`.
- Удаление — обмен с последним элементом (`swap-remove`), поэтому обход плотного
  массива линейный и без ветвлений по «живости»; «мёртвые» слоты помечаются в `EntityRegistry`.
- Переупаковка (`swap-remove`) инвалидирует ссылки вида «сущность + плотный индекс»,
  поэтому наружу отдаётся `Entity`, а не индекс. `EntityRegistry` поддерживает
  обмен позиций при удалении — это делает удаление `O(1)`.

Запрос комбинирует несколько хранилищ:

```csharp
public readonly struct Query<T1, T2> where T1 : struct, IComponent
                                       where T2 : struct, IComponent
{
    public Enumerator<...> GetEnumerator(SystemContext ctx);
}
```

Правила реализации:

- ведущим выбирается самое маленькое хранилище (по `DenseCount` на момент кеша);
- пересечение остальных — по массиву `Entity.Index -> dense slot` плюс проверка поколения,
  без `Dictionary<Type, object>` и без boxing;
- результат запроса кешируется на версию структурного изменения; любое
  `Add`/`Remove` компонента или сущности увеличивает `StructuralVersion`, кеш сбрасывается;
- перечисление даёт `ref`-доступ к компонентам без копирования (`ref T2`, `ref T1`).

Производительность на 10 000 сущностях и 10 системах: вместо 100 000 проверок словаря
на кадр — 10 проходов по плотным массивам, что на порядок быстрее и не аллоцирует.

### 7.5. Трансформации

Трансформация вынесена из компонентов в отдельную подсистему `TransformGraph`,
потому что она нужна почти всем сущностям, участвует в иерархии и требует
пересчёта матриц по грязному флагу.

```csharp
public struct LocalTransform { Vector2 Position; Angle Rotation; Vector2 Scale; float Layer; }
public struct WorldTransform { Vector2 Position; Angle Rotation; Vector2 Scale; float Layer; Matrix3X2 Matrix; bool Dirty; }
```

- `world.Transforms.Local(entity)` — чтение/запись с пометкой грязным.
- `world.Transforms.World(entity)` — мировая матрица, вычисляется один раз
  после обработки грязных узлов (система `TransformUpdateSystem` в конце симуляции).
- Иерархия: `SetParent(child, parent)`, `SetParent(child, null)`, обход детей,
  защита от циклов (проверка достижимости нового родителя в поддереве ребёнка,
  с ограничением глубины — например, 64).
- `Layer` (сортировка отрисовки) — часть трансформации, отделена от `Position.Z`
  (текущий код смешивает слой и третью координату позиции).
- Физика не запрещает иерархию на уровне API: запрет переносится в правило
  «у тела с физикой локальный трансформ не используется, трансформ берётся из тела»,
  реализуемое системой синхронизации и валидатором префабов.

### 7.6. Жизненный цикл сущности

```csharp
var e = world.Spawn();                 // выделяет слот, Generation++, Transform = identity
world.Add(e, new LocalTransform(...)); // или world.Spawn(builder)
world.MarkForDestroy(e, DestroyChildren.Detach);
```

Порядок в конце кадра (в `World.Flush()`), гарантированный и единственный:

1. выполнить отложенные команды из `CommandBuffer`;
2. исполнить события «сущность уничтожена» для подписчиков;
3. вызвать `Dispose` компонентов-ресурсов в порядке добавления;
4. снять из иерархии (дети отвязываются или удаляются согласно флагу);
5. удалить из всех хранилищ компонентов;
6. освободить слот в `EntityRegistry`.

Удаление физического тела и GPU-ресурса происходит внутри этого порядка, а не
в произвольном месте — это устраняет нынешнюю зависимость от порядка обхода словаря.

### 7.7. Префабы и шаблоны сущностей

Вместо `Entity.SourceId` (текущий хак, который хранит «родителя по факту создания»):

```csharp
public interface IPrefabFactory
{
    Entity SpawnPrefab(World world, in PrefabHandle prefab);
    PrefabHandle LoadPrefab(string path);
}
```

Префаб — список «компонент -> фабрика», применяемых к новой сущности.
Сериализация префабов: JSON с типом компонента и его полями (регистрируемые сериализаторы).

## 8. Системы и конвейер обновления

### 8.1. Интерфейсы

```csharp
public interface ISystem
{
    void OnCreate(in SystemContext context);   // регистрация, подписки, чтение конфигурации
    void OnUpdate(ref SystemContext context);  // логика кадра
    void OnDestroy();                           // освобождение подписок и ресурсов
}

public interface IEarlyInitSystem : ISystem { }  // порядок создания, до OnCreate остальных
public interface ILateCleanupSystem : ISystem { } // порядок разрушения, обратный
```

`SystemContext` — структура, передаваемая по `ref`: доступ к `World`, `dt`,
номеру кадра, сервисам, `CommandBuffer`, `Entity`. Через неё система получает всё,
что ей нужно, и не имеет доступа к тому, чего не касается.

### 8.2. Группы обновления вместо числовых приоритетов

Магические числа (`50`, `100`, `200`, `400`, `500`) заменяются явными группами
и атрибутами порядка:

```text
StartupGroup                 OnCreate всех систем, загрузка сцены
├── InputUpdateGroup         опрос ввода, обновление осей и состояний устройств
SimulationGroup              фиксированный шаг 1/60, выполняется 0..N раз за кадр
│   ├── (PhysicsStepSystem)  шаг Box2D
│   ├── EarlySimulation      ввод игрока, намерения
│   ├── Simulation           игровая логика по умолчанию
│   ├── LateSimulation       урон, смерть, таймеры эффектов
│   └── TransformUpdateSystem пересчёт мировых матриц
UpdateGroup                  переменный шаг (UI, анимации, камера)
PreRenderGroup               подготовка кадра: сортировка, сборка батчей
RenderGroup                  проходы отрисовки
```

Внутри группы порядок задаётся атрибутами:

```csharp
[UpdateInGroup(typeof(SimulationGroup))]
[UpdateAfter(typeof(PlayerControlSystem))]
public sealed class WeaponSystem : ISystem { }
```

`UpdateAfter`/`UpdateBefore` разрешаются один раз при `OnCreate` в топологический порядок;
циклы в зависимостях — исключение при старте, а не молчаливая сортировка.

### 8.3. Фиксированный шаг

```csharp
public sealed class FixedStepper
{
    public double TimeStep { get; init; } = 1.0 / 60.0;
    public int MaxSubSteps { get; init; } = 5;
    public double MaxFrameTime { get; init; } = 0.25;  // «схлопывание» паузы
    // аккумулятор, остаток, счётчик выполненных шагов, догоняющие шаги
}
```

Правила:

- `dt` из окна ограничивается `MaxFrameTime` (после сворачивания окна не делается 40 шагов);
- аккумулятор не превышает `MaxSubSteps` шагов, излишек сбрасывается с предупреждением;
- фиксированный шаг используют физика, таймеры и игровая логика с физикой;
- UI, камера, анимации интерполяции идут в `UpdateGroup` по реальному `dt`.

## 9. Сцены

### 9.1. Проблемы текущей реализации и что меняется

| Сейчас | Стало |
|---|---|
| `GScene` владеет сущностями, системами, таймерами, физикой и камерой | `Scene` — описание сцены (системы, проходы, параметры), данные живут в `World` |
| Сцена сама создаёт сущности камеры и физического мира в конструкторе | камера — сервис или компонент, создаваемый явно; физический мир — сервис, подключаемый опционально |
| Переход через очередь из двух действий | конечный автомат состояний с запретом на гонки |
| Нет слоёв сцен | стек сцен: игровая сцена + необязательные оверлеи |
| Нет параметризации | `ISceneFactory<TArgs>` с аргументами перехода |
| Нет загрузки и выгрузки ресурсов по сцене | `AssetScope` на сцену, выгрузка по подсчёту ссылок |

### 9.2. Модель

```csharp
public interface IScene
{
    string Name { get; }
    ValueTask<SceneLoadResult> LoadAsync(SceneContext context, CancellationToken ct);
    void Unload(SceneContext context);
    void Update(in FrameTime time, SceneContext context);
}

public sealed class SceneContext        // всё, что сцена получает снаружи
{
    public World World { get; }
    public AssetScope Assets { get; }
    public IServiceProvider Services { get; }   // физика, ввод, лог, конфиг
    public Camera Camera { get; }
    public IRandomSource Random { get; }
    public CommandBuffer Commands { get; }
}

public interface ISceneFactory<in TArgs>
{
    IScene Create(TArgs args);
}
```

### 9.3. Менеджер сцен и переходы

```csharp
public enum SceneState { None, Loading, Active, Unloading }

public sealed class SceneManager
{
    public SceneState State { get; }
    public IScene? Active { get; }
    public IReadOnlyList<IScene> Overlays { get; }

    public ValueTask SwitchTo<TArgs>(ISceneFactory<TArgs> factory, TArgs args,
                                     SceneTransition transition, CancellationToken ct);
    public ValueTask PushOverlay(IScene scene);
    public ValueTask PopOverlay();
}
```

Правила конечного автомата:

- состояние хранится явно, а не выводится из `CurrentScene != null`;
- `SwitchTo` во время `Loading`/`Unloading` отменяет предыдущий переход через `CancellationToken`
  и ставит новый в очередь; «мёртвая» очередь из двух действий отсутствует;
- переход имеет фазы `Unload -> Load -> (Activate)`, и только после `Activate` сцена
  получает `Update` и рендер;
- ошибка загрузки откатывает состояние в `None` и вызывает `ILogSink.Error`, а не
  оставляет менеджер в промежуточном состоянии;
- оверлеи обновляются и рисуются поверх активной сцены, но не выгружают её ресурсы.

Опционально — переходы с анимацией (`ISceneTransition` с параметрами `duration`,
`fade`, `slide`), реализуемые как обычная система сцены, без специальных случаев в менеджере.

### 9.4. Ресурсы сцены

```csharp
public sealed class AssetScope : IDisposable   // освобождается при выгрузке сцены
{
    public T Load<T>(AssetKey key) where T : class;
    public PrefabHandle LoadPrefab(string path);
    public T Get<T>() where T : class;          // ресурс с постоянным временем жизни
}
```

- Ключи ресурсов — `AssetKey` (строковый путь в логической системе), а не абсолютный путь;
- ресурсы с постоянным временем жизни лежат во внутреннем scope и не выгружаются вместе со сценой;
- подсчёт ссылок: `Retain`/`Release`, ресурс удаляется при нулевом числе ссылок и
  окончании времени жизни сцены;
- отсутствующий ресурс — `Debug`-сообщение плюс заранее определённый ресурс-заглушка
  (для текстуры — шахматный шаблон), а не `null` и не исключение посреди кадра.

### 9.5. Что считается игровым кодом, а что — движком

Движком считается всё, что не содержит правил конкретной игры: ECS, сцены, рендер,
физика, ввод, ассеты, математика. Пример `samples/Sandbox` содержит игровые сущности
(персонаж, пуля, стена), игровые системы и игровые правила. Ни один проект в `src/`
не должен содержать упоминаний конкретных сущностей игры — это проверяется ревью
и поиском по `src/` в CI.

## 10. Рендеринг и спрайты

### 10.1. Цели

- один draw call на материал вместо одного на спрайт;
- явная сортировка отрисовки вместо порядка обхода словаря;
- правильная политика глубины для 2D;
- отсутствие зависимости логики от OpenTK/Box2D и наоборот;
- расширяемость: новый проход отрисовки добавляется без правок существующего кода.

### 10.2. Архитектура

```text
RenderPass (абстракция)          — знает, что рисовать, и вызывает IGraphicsBackend
├── SpriteRenderPass             — спрайты и nine-slice, батчинг и инстансинг
├── DebugLineRenderPass          — линии (отладка физики, следы, отладочные примитивы)
└── UiRenderPass                 — прямоугольники и текст UI (включая полосы здоровья)

SpriteBatcher                    — сборка инстансов: сортировка, нарезка по материалу
Material                         — шейдер + состояние (blend, depth, cull)
IRenderPass, IRenderTarget       — цепочка проходов и целей рендера
```

### 10.3. Компонент спрайта

```csharp
public struct SpriteComponent : IComponent
{
    public TextureHandle Texture;
    public RectI SourceRect;        // регион в текстуре (для атласов)
    public Vector2 Size;            // размер в единицах сцены (или в пикселях при PPM = 1)
    public Vector2 Pivot;           // опорная точка, по умолчанию центр
    public Vector2 Offset;
    public Rgba32 Tint;
    public float Alpha;
    public byte FlipX, FlipY;
    public float Layer;             // сортировка; берётся из TransformGraph, если не задано
    public short MaterialId;        // 0 — спрайтовый, иначе — кастомный материал
    public short SizingMode;        // Pixels / Meters / Stretch(для nine-slice)
}

public struct NineSliceComponent : IComponent
{
    public int Left, Right, Top, Bottom;
}
```

Отличия от текущей реализации:

- компонент — структура без ссылок (кэшируется, не аллоцирует);
- `Texture` становится `TextureHandle` (индекс в реестре ресурсов), а не ссылкой на
  `Texture2D`: это позволяет батчить и освобождать ресурсы без правок компонентов;
- размер, pivot, offset, регион текстуры, tint, флипы, слой — явные поля
  вместо вычисления матрицы внутри компонента (компонент не должен знать про матрицы);
- политика масштабирования переименована и задокументирована: `Pixels` (размер в пикселях),
  `Meters` (размер в единицах физики, умножается на PPM), `NineSlice`;
- nine-slice — отдельный компонент, а не подкласс `GSprite` с девятью методами `new`,
  перекрывающими базовые (текущий код возвращает `GSprite` из `SetTexture`,
  что ломает цепочки вызовов на подклассе).

### 10.4. Батчинг и инстансинг

Порядок кадра для спрайтов:

1. Собрать видимые спрайты запросом `Query<SpriteComponent, WorldTransform>()`.
2. Отсечь камерой (`Aabb` вида в мировых координатах).
3. Отсортировать: по `MaterialId`, затем по текстуре, затем по `Layer`, затем по `Entity`
   для стабильного порядка.
4. Разбить на батчи по `(MaterialId, Texture)` и по лимиту инстансов (например, 4096).
5. Заполнить буфер инстансов: `InstanceData { Vector4 Rect; Vector4 UvRect; Rgba32 Color; }`.
6. Вызвать `DrawElementsInstanced` с единичным quad-мешем и общим VAO инстансов.

Результат: 2-3 draw call на кадр вместо тысяч. Инстансинг требует поддержки
`GL 3.3+`/`OpenGL ES 3.0+`; при более старом контексте включается запасной путь
«развёрнутые четыре вершины на квад» тем же батчером (код батчера общий).

### 10.5. Камера и проекция

Текущий `CreatePerspectiveFieldOfView` в 2D-игре заменяется:

```csharp
public sealed class Camera2D
{
    public Vector2 Position;         // мировая точка в центре вида
    public Vector2 Size;             // размер видимой области в единицах сцены
    public float Rotation;
    public float PixelPerUnit = 16f; // соответствует текущему PPM
    public CameraMode Mode;          // Fixed, FollowTarget, FollowSmoothed, PixelPerfect, Stretch
    public Matrix3X2 View { get; }
    public Matrix3X2 ViewProjection { get; }
    public Rect ViewBounds { get; }
}
```

- `ViewProjection` — `Matrix3X2`, для спрайтов достаточно аффинного преобразования;
- `PixelPerUnit` связывает рендер и физику через один источник истины (было: `PPMScale`
  в физическом компоненте, который использовал рендер);
- камера — обычный объект, а не «компонент-маркер», который ищется в сцене;
  при желании она может быть и компонентом-синглтоном, но API сцены от неё не зависит.

### 10.6. Состояние GL

- `GraphicsState` кэширует текущие шейдер, текстуру, VAO, blend, depth и пропускает
  избыточные вызовы: `BindTexture` на ту же текстуру не вызывается;
- `Shader` компилируется с проверкой лога; при ошибке — исключение с полным текстом лога
  и указанием файла (текущий вариант молча рисует мусор);
- финализаторов у GPU-ресурсов нет: освобождение только явное и в одном месте
  (текущий финализатор `Shader` вызывает `GL.DeleteProgram` из потока финализации);
- шейдеры грузятся из `assets/shaders/<name>.vert|.frag`, имя ресурса совпадает с папкой;
  перечень обязательных шейдеров задаётся конфигурацией, а не «забывается» в коде.

### 10.7. Отладочный рендер

Отладка физики, следы и сетка — один `LineRenderPass` с собственным буфером на кадр,
включаемым флагом конфигурации `debug.drawColliders`. `LineBatcher` перестаёт быть
синглтоном `GLProvider`: у каждого прохода свой экземпляр, поэтому порядок отрисовки
не зависит от порядка регистрации модулей.

## 11. Физика (Box2D)

### 11.1. Абстракция

Физика — сервис, а не компонент сущности. `IPhysicsBackend` позволяет подставить
другую реализацию или заглушку для тестов.

```csharp
public interface IPhysicsBackend
{
    string Name { get; }
    IPhysicsWorld CreateWorld(in PhysicsWorldDescription description);
}

public interface IPhysicsWorld : IDisposable
{
    WorldHandle Handle { get; }
    float PixelsPerMeter { get; }
    Vector2 Gravity { get; set; }

    BodyHandle CreateBody(in BodyDescription description);
    void DestroyBody(BodyHandle body);
    void SetTransform(BodyHandle body, Vector2 position, Angle rotation);
    void SetVelocity(BodyHandle body, Vector2 linear, float angular);
    void ApplyImpulse(BodyHandle body, Vector2 impulse);
    void ApplyForceToCenter(BodyHandle body, Vector2 force);

    ShapeHandle AttachShape(BodyHandle body, in ShapeDescription shape);

    void Step(in StepDescription step);              // фиксированный шаг
    ContactEvents DrainContacts();                   // контакты и сенсоры за шаг
    IReadOnlyList<RayHit> RayCast(in RayQuery query);
    int QueryAabb(in AabbQuery query, Span<BodyHandle> results);
}

public interface IPhysicsEntityMapping
{
    Entity GetEntity(BodyHandle body);
    bool TryGetEntity(BodyHandle body, out Entity entity);
    void Bind(BodyHandle body, Entity entity);
    void Unbind(BodyHandle body);

```

`PhysicsWorldDescription` содержит гравитацию, `PixelsPerMeter`, число подшагов и флаги
(спит ли тело, непрерывная ли столкновения для быстрых объектов).

### 11.2. Интеграция с ECS

```csharp
public struct RigidBodyComponent : IComponent   // структурный
{
    public BodyHandle Handle;
    public BodyKind Kind;         // Static, Kinematic, Dynamic
    public float GravityScale;
    public byte IsBullet;
}

public struct ColliderComponent : IComponent   // структурный
{
    public ShapeKind Kind;        // Circle, Capsule, Box, Polygon, Chain
    public Vector2 Size;          // для Box
    public Vector2 Offset;
    public Angle Rotation;
    public Filter Filter;         // CategoryBits, MaskBits, GroupIndex
    public byte IsSensor;
}
```

- сущности не хранят `B2BodyId`: только `BodyHandle` (`readonly struct` поверх `ulong`);
- `B2BodyId -> Entity` живёт в `IPhysicsEntityMapping` (словарь на стороне бэкенда Box2D);
  обращение из колбэта контакта — один поиск в словаре вместо `b2Body_GetUserData`
  с `GetRef<UserData>` на каждое событие;
- `UserData` в Box2D не хранит ссылки на компоненты: только `ulong` идентификатор сущности
  и версия, что исключает использование освобождённых объектов из нативного колбэка;
- `DrainContacts` возвращает собственные DTO (`ContactEvent` с `EntityA`, `EntityB`,
  `Normal`, `Impulse`, `IsSensor`), без типов Box2D — системам контактов не нужен доступ
  к нативному API.

### 11.3. Порядок кадра и двусторонняя синхронизация

```text
PhysicsPrepareSystem   (SimulationGroup, первый)
    для тел с внешним управлением (Static/Kinematic): TransformGraph -> тело
PhysicsStepSystem      (SimulationGroup)
    world.Step(FixedStepper.TimeStep, subSteps); contacts = world.DrainContacts()
ContactDispatchSystem  (SimulationGroup, после шага)
    раздача событий подписчикам через CommandBuffer (без мутаций в середине обхода)
PhysicsSyncSystem      (SimulationGroup, последний)
    для динамических тел: тело -> TransformGraph (локальная позиция/угол, Dirty = true)
```

Правила, убирающие ручное состояние `IsSynced`:

- синхронизация в обе стороны определяется **видом тела**: `Dynamic` читается из тела,
  `Static`/`Kinematic` пишется в тело. Флагов «синхронизировано» не существует;
- запросы перечисляются один раз и материализуются в буфер на шаг (текущий код
  перебирает `IEnumerable` дважды, между обходами набор сущностей может измениться);
- если тело уничтожено в `CommandBuffer` этого же кадра — оно исключается из обработки
  проверкой `IsAlive(entity)`;
- запрет «родитель-ребёнок для физических тел» остаётся, но реализуется валидатором
  префаба и системой синхронизации (родитель физического тела игнорируется
  при вычислении мировой матрицы), а не исключением внутри `SetParent`.

### 11.4. Отладка

Отрисовка тел (`b2Body_GetShapes` → `b2Shape_Get*` → `LineBatcher`) переносится в
`XEngine.Physics.Box2D/Debug/BodyShapeDebugSource.cs`, возвращающий `ReadOnlySpan<DebugLine>`;
рисующий проход в `XEngine` ничего не знает о Box2D. Точность отрисовки скруглений
задаётся числом сегментов в настройках отладки (текущие константы 8/8/16 — тоже магия).

## 12. Ввод

### 12.1. Абстракция

```csharp
public interface IInputBackend
{
    IInputSource CreateSource(IWindowHandle window);

public interface IInputSource : IDisposable
{
    InputState GetState();                 // снимок текущего кадра
    event Action<InputEvent>? EventRaised;

public readonly record struct InputState
{
    public ReadOnlyMemory<bool> Keys;      // по индексу XEngine.Input.Key
    public ReadOnlyMemory<bool> PreviousKeys;
    public Vector2 MousePosition;          // в пикселях окна
    public Vector2 MouseDelta;
    public float ScrollDelta;
    public MouseButtonMask Buttons, PreviousButtons;
    public ReadOnlyList<Char> TextInput;   // ввод текста
}
```

### 12.2. Собственные перечисления

```csharp
public enum Key { Unknown = 0, A, B, ..., LeftShift, Space, Escape, ... }
public enum MouseButton { Left, Middle, Right }
```

Причина: `GameConfig` сейчас сериализует `OpenTK...Keys`, то есть конфиг привязан
к чужой платформенной нумерации. Собственный `Key` даёт стабильный формат `config.json`
и независимость от бэкенда. В конфигурации ключ записывается именем (`"jump": "Space"`).

### 12.3. Слои ввода

| Слой | Ответственность |
|---|---|
| `InputBackend` (Silk.NET) | опрос устройств, низкоуровневые события, текст |
| `InputSource` | снимок состояния, фронты (`JustPressed`/`JustReleased`), сброс при потере фокуса |
| `InputService` | привязки действий к ключам, оси с инерцией, буферы ввода (буфер «нажал раньше» дляjump) |
| Игровые системы | реагируют на действия: `IsActionJustPressed("jump")` |

Реализация `InputService` на Silk.NET: `window.CreateInput()` + `IInputContext` из
`Silk.NET.Input`, снимок состояния — `CaptureState()` (`KeyboardState`, `MouseState`)
из `Silk.NET.Input.Extensions`.

### 12.4. Исправление семантики действий

| Метод | Смысл |
|---|---|
| `IsDown(action)` | действие удерживается прямо сейчас |
| `IsJustPressed(action)` | переход «не нажато -> нажато» в этом кадре |
| `IsJustReleased(action)` | переход «нажато -> не нажато» в этом кадре |
| `IsActive(action)` | удерживается не меньше заданного времени (hold-time) |

Текущая `IsActionActive` (наличие ключа и в текущем, и в предыдущем кадре) семантически
не соответствует названию: она срабатывает только со второго кадра. Новая `IsDown` без
задержки, `IsActive` — с явно настраиваемым hold-временем.

Сброс предыдущего состояния выполняется **в начале** `Update` ввода, до вычисления
действий и осей, иначе состояние зависит от порядка вызовов (текущая ситуация).

## 13. Конфигурация и данные

### 13.1. Конфигурация

```csharp
public sealed class EngineConfig
{
    public WindowConfig Window { get; init; }
    public RenderConfig Render { get; init; }       // vsync, msaa, clear color, layers
    public PhysicsConfig Physics { get; init; }     // gravity, ppm, subSteps
    public DebugConfig Debug { get; init; }
    public InputConfig Input { get; init; }         // keymap, axes, deadzone
}
```

- конфигурация — иммутабельный объект, собираемый из JSON и перекрываемый аргументами
  командной строки, затем кодом (`ConfigureServices`/`Configure`); приоритет: код >
  командная строка > JSON > значения по умолчанию;
- десериализация через `System.Text.Json` с исходным кодом (`JsonSerializerContext`)
  вместо рефлексии: AOT-совместимость и проверяемость контракта;
- векторы, углы, цвета, перечисления читаются собственными конвертерами
  `XEngine.Mathematics.Serialization` (вместо `OTKVector2Converter`);
- проверка при загрузке: неизвестные имена действий и осей — `Debug`-сообщение со списком
  допустимых, а не молчаливое игнорирование.

### 13.2. Формат ресурсов на диске

```text
assets/
├── config/engine.json
├── shaders/sprite.vert, sprite.frag, line.vert, line.frag, ui.vert, ui.frag
├── textures/player.png, tiles.png
└── prefabs/player.prefab.json
```

`assets/` — общий каталог движка и примеров; ресурсы конкретного примера лежат
в `samples/Sandbox/assets/`. Путь до каталога передаётся в `GameHostOptions`,
а не вычисляется как `AppDomain.CurrentDomain.BaseDirectory + "/Assets"`
(текущий подход привязывает движок к раскладке вывода).

### 15.1. Окно и цикл

- передача `IGL` в конструктор бэкенда позволяет использовать мок в тестах.

`StbImageSharp` остаётся как реализация `IImageDecoder` за интерфейсом; при

### 15.6. Целевой фреймворк

- `net10.0` вместо `net8.0-windows`: кроссплатформенность (Linux, в том числе

- `Nullable enable`, `ImplicitUsings enable`, `LangVersion latest`,
  `TreatWarningsAsErrors` (раздел 16);
- `InvariantGlobalization = true` для тестовых проектов, чтобы тесты не зависели от локали.

## 16. Правила написания кода

### 16.1. Стиль

| Правило | Значение |
|---|---|
| Пространства имён | файловые (`namespace X;`), без отступов внутри |
| Файловые пространства | только в `src/`; в `tests/` — блочные (по требованиям xUnit) |
| Именование типов | `PascalCase`; интерфейсы с `I`; структуры-значения с суффиксом `Description`/`Handle`/`Options` |
| Приватные поля | `_camelCase`; публичные поля запрещены (кроме `const` и `static readonly`) |
| Свойства | только когда есть смысл; вычисляемое свойство без `set` либо с кешем |
| Методы | короткие, одна ответственность; имя — глагол (`TryGet`, `Add`, `Apply`) |
| Асинхронность | `async` только через `CancellationToken`; без `.Result` и `.Wait()` |
| Nullable | ссылочные типы аннотируются; `?` означает «может отсутствовать», а не «заглушка» |
| Исключения | `ArgumentNullException`/`ArgumentOutOfRangeException` для нарушений контракта, `InvalidOperationException` для неверного состояния, `EngineException` для ошибок движка |
| Логи | `ILogSink` (`Error`, `Warn`, `Info`, `Debug`), не `Console.WriteLine` и не `Debug.WriteLine` напрямую |
| Комментарии | объясняют «почему», а не «что»; XML-документация — обязательна для публичного API |
| TODO | только с номером задачи и сроком; запрещён в merges без плана |

### 16.2. Инкапсуляция и состояние

- Внутренние коллекции наружу отдаются как `IReadOnlyList<T>` / `ReadOnlySpan<T>`.
- Никаких `public`-полей и `ref`-возвратов наружу из структур, которые лежат в хранилище.
- Счётчики и кеши приватны; доступ через методы с проверками инвариантов.
- Никаких `static`-сервисов и синглтонов с доступом из кода. Единственное исключение —
  `ILogSink.Null` как заглушка по умолчанию в тестах.
- Магические числа запрещены (`500`, `10f`, `0.101f`, `16f` из текущего кода становятся
  именованными константами или полями конфигурации).

### 16.3. Производительность как требование

- Нет аллокаций в горячем пути: `foreach` по массивам, кеш делегатов, `Span<T>` для
  временных данных, пул буферов для батчей; LINQ допускается только в коде загрузки
  и в инструментах, не в `Update`/`Render`;
- запросы ECS перечисляются без boxing и без `IEnumerable`;
- строки в горячем пути заменяются на `ReadOnlySpan<char>` или идентификаторы;
- структурные изменения выполняются через `CommandBuffer`, поэтому обход в кадре
  не требует копий.

### 16.4. Анализаторы и CI

- `.editorconfig` с включёнными правилами: `CA1062` (проверка null), `CA1819`
  (массивы как `ReadOnlySpan`), `CA2227` (коллекции в параметрах), `CA1848`,
  `CA2007` (`ConfigureAwait`), `CA1031` (не ловить `Exception` без логирования),
  `IDE` — стиль, `dotnet_diagnostic.StyleCop.*` — отключить, документацию вести вручную;
- запрет на `System.Console` и `System.Diagnostics.Debug` вне `ILogSink` —
  пользовательская проверка в CI (grep по `src/`);
- запрет на `using Silk.NET` / `using Box2D.NET` в `XEngine.Core` и `XEngine.Mathematics` —
  та же проверка в CI;
- CI: `dotnet restore`, `dotnet build -warnaserror`, `dotnet format --verify-no-changes`,
  `dotnet test`; все обязательны.

## 19. Риски и открытые вопросы

| Риск | Почему опасен | Что делаем |
|---|---|---|
| Silk.NET требует нативные библиотеки GLFW и GL-контекст | на CI без дисплея тесты с окном не запустятся | тесты не создают окно: `IGraphicsBackend` подменяется заглушкой; окно проверяется вручную |
| Имена методов Silk.NET 3.x отличаются от 2.x | часть таблицы раздела 15 может не совпасть | сверять по `PublicAPI.Shipped.txt` при добавлении каждого вызова; компилятор — источник истины |
| Порядок компонентов меняется при `swap-remove` | системы, полагающиеся на стабильный обход, начнут дрожать | стабильный порядок задаёт сортировка в батчере по `Layer` и `Entity`, а не память |
| `UpdateAfter` и `UpdateBefore` образуют цикл | конвейер не запустится | разрешать топологически при `OnCreate`; цикл — исключение с указанием пары систем |
| Отложенный `CommandBuffer` меняет момент удаления | ресурсы освобождаются не там, где ожидают | порядок в `World.Flush()` фиксирован и покрыт тестом |
| Перенос большого объёма кода за один раз | нельзя проверить промежуточные состояния | этапы раздела 17: после каждого зелёная сборка и тесты |
| Текущий проект не собирается вне Windows | нельзя проверить даже сборку | этап 1 снимает `net8.0-windows`; старый проект удаляется на этапе 10 |

Открытые вопросы, требующие решения до этапа 2:

1. Нужна ли поддержка нескольких окон или достаточно одного.
2. Какой минимальный профиль OpenGL считать допустимым: 3.3 core хватает
   для инстансинга и VAO.
3. Нужен ли текстовый рендер в движке: тогда появляется проект `XEngine.Text`
   и загрузка шрифтов, иначе текст остаётся задачей игры.
4. Сохраняется ли поддержка формата glTF для моделей и атласов.
5. Нужна ли потокобезопасность рендера с отдельным потоком отрисовки
   или достаточно одного потока с фиксированным шагом.

### 21.5. Математика и соглашения

| № | Замечание | Статус | Что в коде |
|---|---|---|---|
| 1 (второй список) | Инвалидация кэша запросов через `Clear()` отсоединяет объект: вызывающий держит осиротевший `CachedQuery` | нет в коде | `CachedQuery`, `StructureVersion` и ленивой инвалидации в проекте нет: запросы перечисляются каждый кадр заново (проблема п.1 и п.2 первого списка). Замечание описывает риск будущей реализации. В новом ECS кэш запроса принадлежит `World` и сбрасывается версией структуры; вызывающий получает `Query<T1,T2>` как структуру без состояния, поэтому осиротеть нечему (раздел 7.4) |
| 2 | Две конвенции поворота: `MathUtils.Rotate` крутит по часовой, `CreateRotationZ` — против часовой | подтверждено | `MathUtils.Rotate` (строка 39) использует `-s * v.X`, `CreateRotationZ` в `GTransform.GetWorldMatrix` — стандартный положительный поворот. `FromPolar` при этом документирован как поворот против часовой стрелки. Важное уточнение к замечанию: **знак нельзя просто «исправить»**, потому что от конвенции зависят направление взгляда и позиция дула в игровом коде. Правильное решение — не менять знак молча, а зафиксировать одну конвенцию в типах (у нас `Angle.Rotate` — против часовой стрелки) и мигрировать игровые формулы вместе с ней, проверяя результат тестом на конкретном повороте |
| 3 | Скалярный путь позиции и матричный считывали поворот в разные стороны: логика думала `(10,4)`, спрайт рисовался `(10,6)` | подтверждено частично | Причина видна в коде и состоит из двух независимых ошибок. Первая: `GTransform.RelativePosition`/`RelativePosition2D` считаются через `MathUtils.Homogenize(_position) * Parent.GetWorldMatrix()`, где `Homogenize` кладёт `v.X` в `Z` — мировая координата `Z` берётся из `X`, то есть пути расходятся. Вторая: `GSprite.Recalculate` строит `rotMat * transMat`, а `GTransform.GetWorldMatrix` — тоже `RotationZ * Translation`, но порядок умножения матриц в OpenTK обратный к привычному, из-за чего скалярный путь (позиция через `MathUtils.Homogenize`) и матричный путь (позиция через `GetWorldMatrix`) дают разные знаки. Нужны две явные функции вместо неявной арифметики |
| 4 | Публичные поля ломают dirty-кэш: присваивание в обход сеттера не помечает матрицу грязной | подтверждено | Публичные изменяемые поля есть в компонентах: `GBox2DBody.Id`, `GBox2DBody.OnCollisionEnter/Exit`, `GBox2DWorld.PixelPerMetre`, `GSprite.FlipX/FlipY`, `GTrace.Color/MaxLength/IsAggressive`, `Axis.Positive/Negative`. `GTrace.MaxLength` и `IsAggressive` читаются системой напрямую, `FlipX/FlipY` применяются в рендере, минуя `GetModelMatrix`, то есть кеш матрицы они не инвалидируют. В `GSprite` при этом `_size`, `_rotation`, `_position` закрыты и меняются только через методы. То есть проблема реальна для части полей и усугубляется тем, что компонент — класс, а не структура: правило «всё состояние через сеттеры» ничем не enforced |

### 21.6. Box2D

| № | Замечание | Статус | Что в коде |
|---|---|---|---|
| 5 | Box2D: тело без фигур не имеет массы, не падает и не принимает импульс | подтверждено | По документации Box2D 3.1 масса тела вычисляется из прикреплённых фигур; без фигур динамическое тело имеет нулевую массу, поэтому импульс не даёт эффекта, и ошибки не возникает. Флагов нет и в `GBox2DBodyBuilder`, ни в коде прикрепления фигур |

### 21.7. Сцены, сервисы, время

| 7 | Общий `IClock` на все сцены ломал изоляцию: у замороженной сцены продолжало идти время активной | нет в коде | Ни `IClock`, ни сервис-контейнера сцены в проекте нет: время передаётся параметром `Update(float dt)` из `GameEngine`, а сцена не может его переопределить. Замечание описывает риск дизайна, которого ещё нет. В новой схеме время принадлежит сцене (`SceneContext`), и у каждой сцены своя пауза и масштаб (раздел 9.2) |
| 8 | `AddService` до `Load` падал в `NullReferenceException` | нет в коде | Реестра сервисов и методов `AddService`/`Get<T>` в проекте нет: зависимости передаются сцене в конструктор (`Assets`, `Input`) и хранятся в полях. Проблема не проявляется, но и защиты нет: `GScene` обращается к `_engine.Assets` и `_engine.Input` напрямую (строки 32-33), то есть подмена невозможна |
| 9 | `Set<object>` терял тип сервиса: `T` выводился как `object`, сервис регистрировался под ключом `System.Object`, `Get<IPhysicsWorld>()` возвращал `null` | нет в коде | Ни контейнера сервисов, ни метода `Set<object>` в проекте нет. Замечание верно как типовая ошибка C#: при хранении в `Dictionary<object,object>` вызов `Set(service)` без явного аргумента типа выводит `T` как `object`, и запись попадает под ключом `System.Object`. В новой схеме сервисы регистрируются только через `AddSingleton<TService, TImplementation>()` с обязательным указанием интерфейса |
| 10 | `AddSystem` был запрещён в `OnLoad` | нет в кода, но риск сохраняется | Явного запрета нет: `GScene.AddSystem` публичен и доступен всегда. Но у системы нет `OnLoad`: жизненный цикл ограничен `Update`, а сортировка по `Priority` выполняется на каждом добавлении (`AddSystem` сортирует список целиком). Если добавить систему во время обхода систем, список изменится в середине цикла, и `foreach` по нему выбросит `InvalidOperationException`. В новой схеме добавление систем разрешено до `StartupGroup`, а порядок фиксируется один раз |

### 21.8. Перенос на Silk.NET: ловушки компиляции

| № | Замечание | Статус | Что в коде |
|---|---|---|---|
| 11 | `VertexAttribPointer` требует `uint stride` и `IntPtr offset`; с `int` выбирается перегрузка с `GLEnum` и сборка падает | подтверждено как риск переноса | В `UnitQuad.Init` и `LineBatcher.Init` вызовы передают `int`: `GL.VertexAttribPointer(0, 2, VertexAttribPointerType.Float, false, 4 * sizeof(float), 0)`. В примерах Silk.NET сигнатура использует `uint` для `stride` и `(void*)0` для смещения, поэтому при прямом переносе вызов не совпадёт и потребует явного приведения типов. Это ловушка именно переноса, а не ошибка текущего кода на OpenTK |
| 12 | `namespace ... .Math` перекрывает `System.Math` | риск, которого сейчас нет | Пространства имён в проекте — `XEngine.Core.*`; пространства `.Math` нет. Замечание верно для будущей математической библиотеки: внутри `namespace XEngine.Math` любой вызов `Math.PI` разрешится в `XEngine.Math` и не соберётся. Поэтому библиотека называется `XEngine.Mathematics` (раздел 6) |
| 13 | Собственный extension `IEnumerable<T>.Count(predicate)` затеняет `Enumerable.Count` и вызывает сам себя, переполнение стека | риск, которого сейчас нет | Собственных расширений для `IEnumerable<T>` в проекте нет. Ошибка реальна: если объявить `public static int Count<T>(this IEnumerable<T> source, Func<T,bool> predicate)`, то внутри тела вызов `source.Count(predicate)` переиспользует сам же метод и даёт бесконечную рекурсию. Решение — использовать `System.Linq.Enumerable` полностью или давать методу другое имя (`CountWhere`) |

Дополнительно найдено при проверке и не указанное в исходном списке:

- `ClearScene()` объявлен, но нигде не вызывается: очистка сцены от сущностей не выполняется ни при выгрузке, ни где-либо ещё;
- `GScene.IsDeleted` проверяется в начале `Update`, но никогда не выставляется в `true`, поэтому ранний выход из `Update` недостижим;
- `IsSynced` не сбрасывается никогда (см. п. 5): после первого изменения позиции `b2Body_SetTransform` вызывается каждый кадр, а документация Box2D 3.1 прямо предупреждает не задавать трансформ тела после создания;
- `BasicHealthRenderModule` и `TracerRenderModule` нигде не регистрируются в `GameEngine.Init`, то есть отображение здоровья и следов не работает;
- шейдер `Rectangle`, используемый `BasicHealthRenderModule`, не загружается (см. раздел 3.5);
- `GScene.RemoveDeleted` вызывает `Transform.SetParent(null)` перед `Dispose`, то есть разрыв иерархии происходит после пометки на удаление, но до освобождения компонентов — порядок зависит от порядка обхода словаря.
