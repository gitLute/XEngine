# XEngine.Mathematics: найденные проблемы

Сводка дефектов математической библиотеки движка, найденных при ревзии
`src/XEngine.Mathematics`. Документ предназначен для планирования исправлений:
каждый пункт содержит место, суть ошибки, ожидаемый и фактический результат,
связанный пробел в тестах.

Документ не меняет требования к движку: он описывает состояние кода на момент
ревзии и расходится с разделом 3 `ARCHITECTURE.md` только тем, что относится к
новой библиотеке, а не к legacy-каталогу `XEngine/`.

### Метод и статус проверки

Ревзия выполнена **чтением исходного кода**. Часть числовых примеров получена
автоматическим анализатором, который успел выполнить библиотеку в отдельном
харнессе **до** того, как ревзия переведена в режим «только чтение»; эти примеры
помечены знаком `≈`. Все шесть критичных дефектов и все существенные подтверждены
статическим разбором исходников независимо от числовых примеров.

Числовые значения из харнесса приводятся справочно и не являются основанием для
исправлений: основание — исходный код.

### Обозначения

## 2. Критичные дефекты (P1)

### P1-1. `Ray3.IntersectsCylinder`: деление на ноль и неверная алгебра

**Место:** `src/XEngine.Mathematics/Ray3.cs:287-340`

**Симптом:** луч, перпендикулярный оси капсулы, молча пролетает сквозь её тело.
Самый частый случай в движке — горизонтальный луч против вертикальной капсулы
персонажа. Результат неверный и в обратную сторону: возможны ложные срабатывания.

**Дефект (a), деление на ноль.** Строка 303:

```csharp
float directionOnAxis = Vector3.Dot(Direction, axis);
float pointOnAxis     = Vector3.Dot(toPointA, axis);

Vector3 offset = toPointA - Direction * pointOnAxis / directionOnAxis;
```

`directionOnAxis` не проверяется на ноль. При `directionOnAxis == 0` выражение даёт
`Inf`, умножение на направление — `NaN` в компонентах. Далее `NaN` проходит мимо
всех проверок, потому что все сравнения с `NaN` дают `false`:

- строка 315 `discriminant < 0f` → `false`, досрочного выхода нет;
- строка 326 `candidate < 0f` → `false`, `continue` не срабатывает;
- строка 332 `along >= 0f && along <= 1f` → `false`.

Метод доходит до строки 339 и возвращает `false`. Тело цилиндра не проверяется,
эндкапсулы его не покрывают, поэтому **капсула не попадает в луч целиком**.
Пример `≈`:

```text
капсула (0,-1,0)-(0,1,0) r=0.5, луч из (-5,0,0), направление (1,0,0)
Intersects = False;  верный вход t = 4.5
```

**Дефект (b), неверные коэффициенты.** Даже при ненулевом `directionOnAxis`
линейный и свободный члены вычислены неверно. При `w = Origin - PointA`,
`axis = B - A` верное уравнение имеет вид

```text
P·t² + 2·C1·t + C0 - r² = 0,
где P = |d_perp|², C1 = dot(d_perp, w_perp), C0 = |w_perp|²,
w_perp = w - axis·dot(w, axis)/|axis|²,  d_perp = d - axis·dot(d, axis)/|axis|²
```

Код использует `toPointA = -w`, что меняет знак линейного члена и меняет его
масштаб (`pointOnAxis / directionOnAxis` вместо `dot(w,axis)·dot(d,axis)/|axis|²`),
а `centerOffsetSquared` несёт лишний член
`2·dot(axis,w)·dot(d,w)/dot(d,axis)`. Пример `≈`:

```text
капсула (0,-2,0)-(0,2,0) r=0.5, луч из (-5,-1,0), направление normalize(1,0.3,0)
код:      P=0.917431 linear=+15.96377 constant=68.19444 → корни -9.8675, -7.5330 (оба отрицательны)
верно:    P=0.917431 linear= -9.578262 constant=24.75000 → корни  4.6981,  5.7422 (вход 4.698)
```

**Пробел в тестах:** тесты на `Ray3` покрывают луч и плоскость корректно,
но неверный результат не ловят, потому что не проверяется перпендикулярный луч
и не проверяется, что луч **начинается внутри** капсулы.

**Исправление:** перейти на стандартную форму коэффициентов
(`w_perp` / `d_perp`), убрать деление на `directionOnAxis` полностью,
оставив единственную проверку `perpendicularSquared <= eps` для случая
параллельности оси.

### P1-2. `Collision.SegmentSegmentDistance`: одна из четырёх пар не проверяется

**Место:** `src/XEngine.Mathematics/Collision.cs:146-151`

```csharp
float distance = Vector2.Distance(p, q);                                   // A.A против B.B
distance = MathF.Min(distance, Vector2.Distance(p, b.ClosestPointTo(p)));         // A.A против отрезка B
distance = MathF.Min(distance, Vector2.Distance(a.ClosestPointTo(q), q));         // B.A против отрезка A
distance = MathF.Min(distance, Vector2.Distance(a.ClosestPointTo(b.B), b.B));      // B.B против отрезка A
distance = MathF.Min(distance, Vector2.Distance(a.ClosestPointTo(b.A), b.A));      // B.A против отрезка A — повтор
```

Строка 148 и строка 150 идентичны, поскольку `q == b.A` (строка 127). Пропущена
пара **`a.B` против отрезка B** — а именно на ней минимум может достигаться,
когда отрезки не пересекаются, и функция возвращает завышенное расстояние.

Минимальный целочисленный пример `≈`:

```text
A = (-3,-3)-(-3,-2),  B = (-3,-1)-(-2,-2)
код = 0.8944;  верно = 0.4472
из кандидатов: A.A–отрезок B = 0.8944 | A.B–отрезок B = 0.4472 (не проверяется)
               B.A–отрезок A = 1.0   | B.B–отрезок A = 1.0
```

**Следствие.** `Collision.Intersects(Capsule2, Capsule2)`
(`Collision.cs:106-116`) сравнивает это расстояние с `r1 + r2`, поэтому
**пересекающиеся капсулы сообщаются как разделённые**. При фаззинге это
около 0.5 % случайных пар `≈`.

**Пробел в тестах:** `CollisionTests.cs` проверяет разделённые и очевидно
пересекающиеся пары; случай, где минимум достигается на пропущенной паре,
не проверяется.

**Исправление:** строка 150 должна быть
`Vector2.Distance(a.B, b.ClosestPointTo(a.B))`.

### P1-3. `Matrix4x4Extensions.GetRotation`: столбцы вместо строк

**Место:** `src/XEngine.Mathematics/Matrix4x4Extensions.cs:259-287`

```csharp
Vector3 scale = matrix.GetScale();          // строки 241-245: длины СТРОК
Matrix4x4 rotation = new(
    matrix.M11 / safeX, matrix.M12 / safeY, matrix.M13 / safeZ, matrix.M14,
    matrix.M21 / safeX, matrix.M22 / safeY, matrix.M23 / safeZ, matrix.M24,
    matrix.M31 / safeX, matrix.M32 / safeY, matrix.M33 / safeZ, matrix.M34,
    ...);
return Quaternion.CreateFromRotationMatrix(rotation);
```

`GetScale` (строки 241-245) вычисляет масштаб как длины **строк** матрицы.
`GetRotation` делит элементы на масштаб по **столбцам**. Это противоречит и
собственному соглашению библиотеки, записанному в шапке того же файла
(строки 10-13: правосторонняя система, Y вверх, **вектор-строка**, `v * M`,
матрица поворота хранит в строках образы базовых векторов), и комментарию
на строке 266, который утверждает обратное.

Следствие: возвращается не-единичный кватернион с произвольным углом, а
`Matrix4x4.CreateFromQuaternion` дополнительно масштабирует геометрию на `|q|²`.
Пример `≈`: `CreateTRS(0, Rz(90°), scale(2,3,4)).GetRotation()` даёт
`{0, 0, 0.766, 0.707}` при `|q| = 1.0425` вместо `{0, 0, 0.7071, 0.7071}`.

**Пробел в тестах:** `Matrix4x4Tests.cs:329` (`GetRotation_RoundTripsQuaternion`)
и `:344` (`GetRotation_IgnoresUniformScale`) проверяют только равномерный
масштаб и чистый поворот — ровно те случаи, в которых деление на масштаб
корректно. Проверки на неравномерном масштабе нет.

**Исправление:** делить строку `i` на масштаб `i`, то есть `M1j / sx`,
`M2j / sy`, `M3j / sz`. Это согласуется с `GetScale` и со строкой 254
документации («длины строк нормализуются»), которая сейчас не соответствует коду.

### P1-4. `Rect.Rotate`: вызван не тот конструктор

**Место:** `src/XEngine.Mathematics/Rect.cs:229-235`

```csharp
public Rect Rotate(Angle angle, Vector2? pivot = null)
{
    Vector2 origin = pivot ?? Center;
    Vector2 rotation = angle.Rotate(new Vector2(X, Y) - origin) + origin;
    Vector2 opposite = angle.Rotate(new Vector2(Right, Bottom) - origin) + origin;
    return new Rect(rotation, opposite);          // это конструктор (позиция, размер)
}
```

Конструктор `Rect(Vector2 position, Vector2 size)` объявлен на строках 31-34 и
принимает **размер**, а не второй угол. `opposite` — абсолютная координата
угла в мире, и она становится Width и Height.

Ошибка проявляется **даже при нулевом повороте**:

```text
Rect(10, 10, 4, 2).Rotate(0°)  →  Rect(10, 10, 14, 12)
```

То есть выбор пивота и применение угла не проверяются никогда.

Дополнительно: даже после исправления на `opposite - rotation` результат не будет
ограничивающим прямоугольником повёрнутого `Rect`. Для получения AABB нужно
повернуть все четыре угла и взять `min`/`max`, как это правильно делает
`Aabb3.Transform`.

**Пробел в тестах:** теста на `Rect.Rotate` нет.

**Исправление:** развернуть четыре угла относительно пивота и собрать результат
через `Rect.FromCorners` (строки 107-112), либо, если нужен именно повёрнутый,
а не осевой прямоугольник, честно переименовать метод и вернуть `Aabb2`.

### P1-5. `Curves.InBack`: дословная копия `OutBack`

**Место:** `src/XEngine.Mathematics/Curves.cs:125-129`

```csharp
public static float InBack(float t, float overshoot = 1.70158f)
{
    float x = t - 1f;
    return x * x * ((overshoot + 1f) * x + overshoot) + 1f;   // это OutBack
}
```

Строки 137-141 (`OutBack`) содержат **тот же текст**. У Пеннера
`easeInBack = t²((s+1)t − s)` — кривая проваливается ниже нуля, в этом и состоит
«перелёт назад». В коде этого нет: на `t = 0.2` кривая выдаёт `≈ 0.706` вместо
`≈ -0.055`.

**Пробел в тестах:** `InterpolationAndCurvesTests.cs:192`
(`EaseCurves_StartAtZeroAndEndAtOne`) проверяет только `InQuad`, `OutCubic`,
`InOutSine`, `OutBounce`. `InBack` и `OutBack` не вызываются вообще. Даже если
бы вызывались на концах, тест прошёл бы: обе кривые дают 0 и 1 при `t = 0` и `t = 1`.

**Исправление:** `t * t * ((overshoot + 1f) * t - overshoot)`.

Остальные кривые сверены с эталонными и корректны: `In/Out/InOutSine`,
`In/Out/InOutExpo`, `In/OutElastic`, `OutBounce`, `In/Out/InOutQuad`,
`In/Out/InOutCubic`, `QuadraticBezier`, `CubicBezier`.

### P1-6. `Rgba32JsonConverter`: альфа всегда `0` для массива из трёх чисел

**Место:** `src/XEngine.Mathematics/Serialization/JsonConverters.cs:139-144`

```csharp
Span<float> values = stackalloc float[4];
JsonArrayReaderHelper.ReadFloatArray(ref reader, values);
return new Rgba32(values[0], values[1], values[2], values.Length == 4 ? values[3] : 1f);
```

`Span<T>.Length` — свойство времени выполнения, а `stackalloc float[4]` всегда
имеет длину 4, поэтому условие **всегда истинно** и ветка с `1f` недостижима.
Непрочитанный слот `stackalloc` равен нулю, поэтому
`"color": [1, 0.5, 0.2]` даёт `Rgba32(1, 0.5, 0.2, 0)` — **полностью
невидимый цвет**.

**Пробел в тестах:** `RandomAndColorTests.cs:340`
(`JsonConverters_ReadColorFromChannelArray`) использует массив из **четырёх**
элементов `[0.5, 0.25, 1, 0.5]`, где альфа приходит явным числом.

**Исправление:** считать реально прочитанные элементы. `ReadFloatArray`
(`JsonArrayReaderHelper.cs:31-42`) должен возвращать их количество, и конвертер
должен подставлять `1f`, когда прочитано три элемента.

| `Capsule3.cs:171` | Порог вырождения `1e-8` сравнивается и с `lengthSquared` осей, и с `MathF.Abs(denominator)` — а это площадь в единицах в четвёртой степени. Смешение единиц в одном пороге |

### 4.4. Прочее

- `Angle.RotateDirection` (`Angle.cs:162`) нормализует, а `VectorExtensions.RotateDirection`
  (`VectorExtensions.cs:33-34`) использует `angle.Direction * vector.Length()`. Результаты
  совпадают, но реализации различаются, а правило библиотеки требует одну реализацию
  на операцию.
- `Angle.Scale` (`Angle.cs:135`) не нормализует результат, а `operator /`
  (`Angle.cs:283`) нормализует. Расхождение задокументировано, но вводит в заблуждение
  при арифметике в цикле.

## 5. Что реализовано корректно

Фиксируется отдельно, чтобы при исправлениях это не переписали по незнанию.

- **`Frustum.cs`** — извлечение плоскостей из view-projection корректно для конвенции
  вектор-строка и диапазона `[-1; 1]`: суммы по строкам легли точно на `M1x..M4x`.
  Все шесть плоскостей нормализуются вместе со смещением через `Plane3.FromCoefficients`,
  знак теста `dot(n,p) + d >= -r` соответствует построению. `ProjectedRadius` —
  точная опорная функция параллелепипеда. Против собственной проекции движка
  расхождений нет `≈`.
- **`Ray3.IntersectsBox`, `Ray2.Intersects(Aabb2)`** — слэб-метод корректен: нулевые
  компоненты направления не дают `NaN`, порядок `tMin`/`tMax` через обмен верный,
  `tMin` стартует с 0, граница включительная `≈`.
- **`Ray3.Intersects(Plane3)`** — `t = -DistanceTo(O)/dot(d,n)` верен, параллельность
  и компланарность отбрасываются согласно документации.
- **`Collision.TryGetObbPenetration`** — SAT корректен: все четыре оси обоих
  прямоугольников, нормализация осей, выбор оси минимального перекрытия и
  ориентация от A к B `≈`.
- **`Collision.Contains(point, center, size, rotation)`** — порядок обратного
  преобразования верен для конвенции вектор-строка.
- **`Matrix4x4Extensions`** — `CreateTRS` (порядок масштаб → поворот → перенос),
  `CreateLookAt` (совпадает с `Matrix4x4.CreateLookAt`, определитель +1, взгляд
  даёт `viewZ = -1`), `CreateViewProjection` (`view * projection` — порядок,
  обратный привычному, но верный для `v * M`), `CreatePerspective` и
  `CreateOrthographic` с диапазоном `[-1; 1]`, `TryInvert` (делегирует BCL,
  рукописного adjugate в библиотеке нет), `MultiplyPoint`, `MultiplyVector`,
  `GetTranslation`, `GetScale`, `TransformNormal` (корректно считает `n · M⁻ᵀ`).
- **`Matrix3x2Extensions`** — порядок пивота, масштаба, поворота и переноса, знак
  поворота (против часовой стрелки), `Rotation()` через `atan2(M12, M11)` корректен
  и при неравномерном масштабе, `ToMatrix4x4` кладёт перенос в `M41`/`M42`.
- **`QuaternionExtensions`** — `FromEuler`/`ToEuler` (порядок и знаки), ветвь
  блокировки gimbal-lock, `FromAxisAngle` (нормализует ось), `Slerp` (ограничивает
  `t`, нормализует результат, корректен при почти параллельных входах),
  `Conjugate` и `Inverse` корректно разведены, `LookRotation` строит ортонормированный
  базис с определителем +1.
- **`Angle`** — `NormalizeRadians` через `Math.IEEERemainder` даёт корректный
  диапазон; `ShortestDelta`, `Lerp` и `MoveTowards` по кратчайшей дуге корректны,
  включая переход через ±π.
- **`Interpolation.Damp`** — `1 − exp(−λ·dt)` действительно не зависит от частоты
  кадров и возвращает `current` при `dt = 0`. `Lerp`, `LerpClamped`, `MoveTowards`,
  `InverseLerp`, `Repeat`, `Repeat01`, `PingPong`, `Clamp`, `Clamp01` корректны.
- **`Rgba32.cs`** — разбор `#RRGGBB` и `#RRGGBBAA` с проверкой длины до среза,
  `FormatException` переупаковывается с контекстом, каналы ограничиваются при
  создании, `ToByte` округляет и ограничивает, `ToString()` выдаёт 8 hex-цифр и
  проходит обратно через `FromHex`, `ToVector4()` упорядочен RGBA.
- **`Random/XorShift64Star.cs`** — обнуление зерна (строка 19), сдвиги на `ulong`,
  `NextFloat` через 24 значащих бита даёт ровно `[0; 1)`.
- **`Capsule3.ClosestPointsBetweenSegments`** — корректный порт RTCD с
  обработанными ветвями вырождения и параллельности `≈`.
- **`BoundingSphere.cs`** — `FromAabb` (центр и половина диагонали) охватывает
  параллелепипед, `Contains`/`Intersects`/`DistanceTo`/`ClosestPointOnSurface`/`Union`
  корректны. Методов `Transform`/`Scale` у типа нет, поэтому ошибки масштаба
  радиуса при неравномерном масштабе в коде отсутствуют.

## 6. Системная причина: тесты проверяют только вырожденные случаи

Общая черта всех дефектов P1: **тест рядом есть, но проверяет именно тот вход,
на котором баг не проявляется.**

| Дефект | Тест рядом | Почему проходит |
|---|---|---|
| P1-3 `GetRotation` | `Matrix4x4Tests.cs:329`, `:344` | только равномерный масштаб и чистый поворот |
| P1-5 `InBack` | `InterpolationAndCurvesTests.cs:192` | `InBack` не вызывается вообще; на концах кривой обе формы дают 0 и 1 |
| P1-6 `Rgba32` JSON | `RandomAndColorTests.cs:340` | только массив из четырёх элементов |
| P1-2 `SegmentSegmentDistance` | `CollisionTests.cs` | разделённые и очевидно пересекающиеся пары |
| P1-1 `IntersectsCylinder` | тесты на `Ray3` | нет перпендикулярного луча и старта внутри |
| P1-4 `Rect.Rotate` | — | теста нет |
| P2 `NextInt` | `RandomAndColorTests.cs:66` | диапазон `(5, 9)` |

Контракты заявлены в XML-документации и покрыты тестами на **типичных**
входах, но не на **невырожденных**. README требует тестов на композицию,
обращение и порядок преобразования точки — они есть, но ровно в том подмножестве,
где регрессия не видна.

Чинить это в обратном порядке нельзя: пока нет теста, падающего на дефект,
правка неотличима от улучшения, которое ничего не сломало.

## 7. Порядок исправления

1. **Сначала тесты, которые падают.** По одному на каждый дефект P1 и P2,
   на невырожденных входах. Это делает правку проверяемой локально.
2. **Затем P1**, в порядке влияния на движок:
   `Ray3.IntersectsCylinder` → `Collision.SegmentSegmentDistance` →
   `Matrix4x4Extensions.GetRotation` → `Rect.Rotate` → `Curves.InBack` →
   `Rgba32JsonConverter`.
3. **Затем P2** — они дешёвые и снимают целый класс тихих отказов.
4. **Затем P3** — сначала те, что меняют соглашения
   (`CreateOrthographic2D`, `Rect.Intersects`, докутрина `LookRotation`),
   потом валидация и переполнения.
5. **После каждой группы** — обновить `README.md` библиотеки, где перечислены
   обязательные тесты, чтобы новые случаи вошли в контракт.
